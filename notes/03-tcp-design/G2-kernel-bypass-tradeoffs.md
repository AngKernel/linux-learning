# G2. kernel-bypass：缩小服务范围后，哪些成本可以重新分配

本篇回答：用户态栈为何能省一些开销？内核提供的哪些保证需要自行补上？前置阅读：G1 与 A–F 各主题。预计阅读：10 分钟。源码基准：Linux v6.18；本文为基于前文证据的架构归纳。

## 1. 问题

专用服务控制 CPU、NIC 队列、应用 API 与内存池后，不一定需要每个包都穿越通用 socket 边界。但“跑在用户态”不自动保证少复制、无锁或安全；关键是选了哪些限制条件。

## 2. 约束

可靠传输、网络拥塞和不可信对端不会因特权级改变而消失。多租户隔离、调试可观测性、故障恢复与管理员策略仍是系统需求。CPU/设备资源有限，专用服务只是可以把某些承诺从每包运行期检查移到部署与应用契约。

## 3. 方案：逐项标出省掉的边界及接手者

| 内核提供的机制/契约 | 专用用户态栈可改变的前提 | 随之需要承担的责任 |
|---|---|---|
| socket syscall 与用户缓冲导入，G1 | 应用直接调用库、共享受控缓冲 | API 不再天然等同 POSIX；明确异步所有权与错误语义 |
| 普通复制后的应用缓冲可复用，A3 | 直接引用应用或 DMA buffer | 引用/归还、重传前不可修改、资源耗尽处理 |
| 任意线程与 softirq 访问 socket，B1/B2 | 每连接单 worker 所有权 | 跨核转交、负载倾斜、停止/迁移与对象回收 |
| socket/protocol/memcg 记账，A2 | 固定池或应用预算 | 按流/租户限额，避免小包元数据放大 |
| NAPI/调度的共享 CPU 机制，C1/C4 | 专核持续 poll | 空闲能耗、同核任务饥饿和过载公平性 |
| 系统 LSM/命名空间等连接边界，G1/B2 | 数据流不经相同内核 socket 路径 | 在设备、进程、控制面与栈内部重建所需策略 |
| TCP 完整状态与防异常报文，D4/F | 实现子集或限制部署网络 | 明确缺失语义、互通范围、漏洞修复与回归测试 |
| 内核 tracing/诊断生态，G1 | 自己的 event/counter | 能解释丢包、队列、重传与卡顿的可观测性 |

这是“责任转移”表，不是宣称用户态必然失去所有隔离。进程地址空间隔离仍存在；内核也仍负责内存、设备管理等基础服务。某个用户态栈可以自行实现更严格的预算和检查，但那部分成本需要计入总系统。

## 4. 演进：内核也在允许应用缩小默认承诺

| 内核 commit / 作者 | 如何减少某类成本而保留主体语义 | 正文数据 |
|---|---|---|
| `f214f915e7db` / Willem de Bruijn | MSG_ZEROCOPY 让应用显式承担发送缓冲生命期，保留内核 TCP。 | 两主机 10 流示例系统 cycles 最多省 20%，范围与限制见 A3。 |
| `0baf26b0fcd7` / Martin KaFai Lau | BPF CC 加快算法更新，复用内核可靠传输与验证框架。 | 该提交未提供性能数据。 |
| `218af599fa63` / Eric Dumazet | 内部 pacing 解除必须采用 fq 的部署约束。 | 800 流实验同时报告吞吐/中断变化，详见 D2，不能概括为统一成本下降。 |

这些不是 kernel-bypass 的起源史，而是可追溯的反证：优化不只有“整栈内核/整栈用户态”两个开关，很多边界可以局部调整。

## 5. 取舍：必须对等比较功能与运行条件

高吞吐测量若忽略 TIME_WAIT、重传、防攻击、加密或空轮询，就可能比较了不同任务。只测单流又无法回答多租户公平与连接风暴下的行为。G1 的归一化方法要再加一列“提供了哪些协议与系统保证”。

用户态专用模型在固定拓扑、可控应用、专核与队列归属明确时，有条件减少通用同步与切换；这是由前述机制推导的场景判断，不是本任务测得的普遍优劣。任意线程模型、广泛设备兼容与系统策略越重要，需要补回的机制就越多。

## 6. 用户态对照：以已读代码区分实现和愿望

Seastar 固定提交 `e417c0c0ebeb1f0578b1dd5b3dd4f65decff0a4b` 文档把连接固定到 shard；这能让应用与协议状态协同规划。[教程源码](https://github.com/scylladb/seastar/blob/e417c0c0ebeb1f0578b1dd5b3dd4f65decff0a4b/doc/tutorial.md#L1666) 但它还有 POSIX 后端，不能按库名判断是否 bypass。

同一提交 native TCP 的 `do_time_wait()` 在 `include/seastar/net/tcp.hh:618` 留有未实现 TIME_WAIT timer 的 FIXME，并设置状态后调用 cleanup。[固定源码](https://github.com/scylladb/seastar/blob/e417c0c0ebeb1f0578b1dd5b3dd4f65decff0a4b/include/seastar/net/tcp.hh#L618) 这是该版本具体路径的实现限制；本篇未据此评判所有 Seastar 部署，也没有运行互通复现。它说明协议完整性必须读代码确认，不能从性能框架名推定。

## 7. 验证

先填一张实际部署能力表：内核/native 后端、零拷贝生命期、计时精度、拥塞算法、关闭状态、TLS、可观测性和隔离配置，再进行相同 CPU 配额、NIC、负载与完整数据校验的性能实验。空闲与满载都计 CPU；重传和丢包恢复要做功能回归。本文未运行用户态栈，也没有编写其实现代码。

## 要点回顾

- 能省什么，取决于限制了哪些自由度。
- 协议、安全与隔离责任会转移，不会自动消失。
- 混合方案允许只优化一部分边界。
- 比较之前先核对同等语义。

## 自测

4. 缺失关闭状态的实现与完整内核吞吐能直接比较吗？

## 与 DPDK/VPP 的对照

熟悉的数据面优化是基础：批处理、局部性、池化和亲和性。把它们用于 TCP 后，还要加上可靠字节流、定时恢复、关闭后的协议记忆与敌对输入审计；这些是包转发经验之外必须补齐的保证。
