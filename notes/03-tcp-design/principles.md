# 从 20 个主题提炼的 12 条设计原则

本篇回答：哪些取舍贯穿 TCP？哪些原则迁到用户态仍成立，哪些可因缩小服务范围而省掉？前置阅读：A–G，至少先读 A1、B1、C3、D2、F2、G1。预计阅读：12 分钟。证据基准：Linux v6.18；每条均链接到至少两个已核对主题。

以下是从源码、注释和历史归纳的设计原则，不是内核作者共同发布的规范。用户态一栏必须连同限定条件阅读；执行位置本身不决定答案。

| 原则 | 至少两个主题的具体证据 | 用户态协议栈中如何变化 |
|---|---|---|
| 1. 分离数据、描述符与各方的生命周期 | [A1](A1-sk_buff.md)：clone 复制元数据而共享载荷；[A3](A3-zero-copy.md)：完成通知管理应用页生命期；[D4](D4-timewait-minisock.md)：应用关闭后只留下必要协议记忆。 | **继续成立**。应用、设备和可靠重传不会同时结束。更强的应用契约能减少适配分支，不能消除所有权。 |
| 2. 用批量摊薄固定成本，同时给批次设边界 | [C1](C1-napi-budget.md)：NAPI RX/时间预算；[C2](C2-gro-gso-tso.md)：GRO/GSO 减少软件对象；[A2](A2-socket-memory.md)：额度批处理减少共享记账。 | **被放大**。专核与固定池便于更大批次，但应用任务和 timer 仍会被过长批次拖延。 |
| 3. 少写共享 cache line，先明确状态的所有者 | [B2](B2-socket-lookup-rcu.md)：RCU 查表避免读锁写入；[B3](B3-multicore-listener.md)：request 独立查找降低 listener 竞争；[A2](A2-socket-memory.md)：per-CPU 额度缓存。 | **被放大**。按 shard/worker 分流后可把共享写转成本地更新；跨核迁移仍需协议。 |
| 4. 需要的状态越少，生命周期就越容易扩展 | [D4](D4-timewait-minisock.md)：tw 保留结束阶段必要信息；[F1](F1-syn-flood-syncookies.md)：cookie 不跨握手等待保留半连接。 | **继续成立**。状态削减必须保留所承诺的协议语义；简单删除 TIME_WAIT 不是等价优化。 |
| 5. 能力可选时保留明确的正确性退路 | [C2](C2-gro-gso-tso.md)：硬件不能分段就软件 GSO；[D2](D2-pacing-edt.md)：fq 不接管时内部 pacing；[A3](A3-zero-copy.md)：普通 ZC 可能复制回退，devmem 不可读时不能如此。 | **继续成立**。固定硬件可省掉某些退路，但要把不支持变成明确失败或部署前提。 |
| 6. 资源限额必须同时约束字节、对象与处理次数 | [A2](A2-socket-memory.md)：truesize 与多层额度；[F2](F2-security-evolution.md)：SACK 段数、skb 碎片化与低 MSS 放大；[C1](C1-napi-budget.md)：CPU 工作预算。 | **继续成立**。固定池只限对象，不自动限每包 CPU 或租户公平；极端输入仍需审计。 |
| 7. 保持进展和限制滥用要共同证明 | [F2](F2-security-evolution.md)：拆分限额后补正常重传例外；[A2](A2-socket-memory.md)：压力/最低保证/硬限的协调；[C3](C3-tsq-bql-autocork.md)：TSQ 的恢复与避免停滞条件。 | **继续成立**。只证明“不会超限”而没证明“有空间后能恢复”，仍可能造成拒绝服务。 |
| 8. 时间精度按用途支付成本 | [D1](D1-timers.md)：大量 timeout 与 pacing hrtimer 分工；[D3](D3-rtt-rto-ack.md)：微秒估计不等于 timer 微秒执行；[C4](C4-busy-polling.md)：轮询用 CPU 换等待。 | **继续成立**。用户态可合并事件循环调度，但 timer、轮询和应用工作仍争 CPU。 |
| 9. 将策略做成接口，核心维护共同的不变量 | [E1](E1-congestion-control.md)：CC ops 共用可靠 TCP；[E2](E2-ulp-bpf-hooks.md)：ULP/sockops 各有状态与访问边界。 | **继续成立**。VPP 也用拥塞操作表；更新更自由时更需自行证明回调与生命周期契约。 |
| 10. 把队列放在还能控制公平与时机的位置 | [C3](C3-tsq-bql-autocork.md)：TSQ/BQL 避免过量压入下层；[D2](D2-pacing-edt.md)：EDT 分离允许时刻与调度释放。 | **被放大**。绕过 qdisc 后应用需自己管 per-flow 与 NIC 队列；burst 发送不能替代节奏和背压。 |
| 11. 用通用同步兼容任意应用线程与执行上下文 | [B1](B1-socket-lock-backlog.md)：进程/softirq 的双重锁与 backlog；[E2](E2-ulp-bpf-hooks.md)：扩展受 socket 上下文约束；[G1](G1-send-recv-cost.md)：系统调用与等待路径。 | **不再必要（有条件）**：若应用承诺每连接单执行者，可以省去同一套任意线程 socket 交接机制；共享表、迁移或并发访问出现时仍需新的同步。 |
| 12. 优化必须保留可说明的语义与可复查证据 | [G1](G1-send-recv-cost.md)：同等数据消费、归一化 CPU；[F2](F2-security-evolution.md)：初始安全修复后仍要验证正常进展；[G2](G2-kernel-bypass-tradeoffs.md)：功能缺口不能混成性能收益。 | **继续成立**。省掉保证可以是产品选择，但必须列出差异，不能拿不同任务的吞吐宣称实现更优。 |

## 把原则应用到自己的栈设计

读到一个“优化”时，用这条因果链检查：

```mermaid
flowchart LR
    P[具体负载与问题] --> I[必须保留的不变量]
    I --> O[数据与状态归谁]
    O --> R[限额与恢复条件]
    R --> M[同等语义下测量]
    M --> L[记录适用范围和代价]
```

例如计划“所有 TCP 数据放固定池，每流一个 worker，批量发送”：A1/A3 要回答设备与重传何时释放；B2/B3 要回答流迁移；C1/D1 要回答批量期间 timer 是否饥饿；C3/D2 要回答设备排队和发送时间；F2 要回答低 MSS、异常 ACK 会不会放大对象或 CPU。这里是设计审题，不包含用户态 TCP 实现代码。

## 可验证与未验证的范围

每条证据都来自对应章节列出的 v6.18 位置和实际读取的历史；用户态对照固定了版本。表中的“被放大/不再必要”是有前提的架构推断，不是性能实验结果。本批未运行 v6.18 VM、用户态栈或硬件卸载测试；运行验证入口见各篇第 7 节，集中测量方法见 G1。

## 要点回顾

- 很多性能优化是在重新划分所有权、状态量和执行时机。
- 批处理与局部性始终受公平、延迟和资源边界约束。
- 硬件/用户态下沉会转移责任，不会消除协议不变量。
- 安全、正常进展与同等语义测量要一起验证。

## 自测

1. 为什么“零拷贝 + 单 worker”仍不能只按 TX completion 回收所有 TCP 数据？
2. 固定池为什么不能单独解决 SACK/低 MSS 资源放大？
3. 什么前提下可以省掉 Linux 的双重 socket 锁？
4. 如何识别一个吞吐提升来自省工作而非等价实现优化？

<details><summary>答案</summary>

1. 重传与应用/设备生命期不同，仍须留到协议不再需要。2. 池限制容量，却不自动限制遍历、段数与每字节 CPU。3. 连接状态单执行者、没有任意线程/softirq 同时进入；跨核交接仍须同步。4. 检查功能、数据完整性、关闭状态、CPU 配额与空轮询是否对齐，再归一比较。

</details>

## 与 DPDK/VPP 的对照

可以继续使用 burst、mempool、RSS 和 worker 的经验，但 TCP 使对象生命周期跨越 RTT、重传和关闭等待。最值得沿用的不是“永远绕过某层”，而是明确每层原来负责什么，再决定由哪个组件继续承担。
